# iumrah — перенос старого Cloudflare без замены API-контракта

Версия: 2026-11-07. Источник схем: `iumrah-old-cloudflare-d1-audit.zip` (структуры таблиц, без записей).

## Что делает пакет

GitHub Actions запускается в одном из трёх режимов:

1. **dry-run**: чтение старых D1, создание *локальной* отфильтрованной копии SQL и безопасного отчёта по количествам. Не пишет ни в один Cloudflare.
2. **import**: тот же экспорт, затем создание отсутствующих D1 в новом аккаунте, импорт в **пустые** базы и сравнение количества записей/внешних ключей. Старые базы не изменяются. Публичные API не переключаются.
3. **copy-r2**: отдельное копирование и побайтовая проверка файлов, на которые ссылаются перенесённые негостиничные таблицы, из `iumrah-hotels-media` в `iumrah-operations-media` нового аккаунта. Фотографии каталога отелей не включены.

Содержимое личных данных, SQL с записями и бинарные документы хранятся только во временной файловой системе GitHub runner. В артефакт загружаются **только сводные количества**.

## Куда переносим

| Старый D1 | Новый D1 | Пояснение |
|---|---|---|
| `iumrah-hotels` | `iumrah-core` | 19 гостиничных таблиц + ссылки доступа к гостиничному монитору исключены; прочие таблицы и идентификаторы остаются |
| `iumrah-web-db` | `iumrah-web-db` | Брони и операции сайта |
| `anonymous-chat-db` | `anonymous-chat-db` | Отдельный модуль; оставляем собственную БД |
| `auto-sale-umar-db` | `auto-sale-umar-db` | Отдельный проект; сохраняем отдельную БД, поскольку запрошен перенос ВСЕХ D1 |
| `iumrah-mcp-oauth` | `iumrah-mcp-oauth` | Пустая исходная D1; создаём пустую БД, если нет |

Существующую новую `iumrah-flights` **не удаляем и не перезаписываем**. Старые авиарейсы будущих дат сохраняются в исходной таблице `curated_flight_offers` внутри `iumrah-core` для совместимости старого API. Их нормализация в Flight Hub — отдельный контролируемый этап.

## Фильтрация

- `curated_flight_offers`: только рейсы с датой вылета от даты запуска по времени Ташкента, и с неистекшей датой обратного сегмента.
- Старые поисковые/проверочные кэши авиарейсов очищаются. `business_flight_sync_feeds`: учётная запись и хэш токена остаются, а устаревший снимок рейсов сбрасывается до пустого; бот наполнит его вновь.
- Временные `storefront_package_*` и `storefront_flight_refresh_progress` очищаются: содержат старые цены/отели; должны пересоздаться с актуальным гостиничным API.
- История оформленных броней, оплаченных пакетов, документов и использованных рейсов **не удаляется**, даже если их даты прошли.
- Гостиничные поля внутри истории бронирований сохраняются как часть исторических записей.
- Две ссылки FK из `trip_assignments` на удалённую таблицу `hotels` убираются, сами значения `makkah_hotel_id`/`madinah_hotel_id` сохраняются. Это единственная известная вынужденная правка constraints; логический API не меняется.

## Установка

1. Добавить файлы этого пакета в репозиторий iumrah Business. Его ZIP-распаковщик принимает имя `iumrah-business-*.zip`.
2. Ручным коммитом добавить `.github/workflows/iumrah-cross-account-d1.yml` из отдельного вложенного файла (распаковщик защищает `.github/workflows`).
3. В GitHub Settings → Secrets and variables → Actions использовать старые секреты `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` (или `OLD_...`). Для копирования в новый аккаунт добавить **только** `NEW_CLOUDFLARE_ACCOUNT_ID` и `NEW_CLOUDFLARE_API_TOKEN`. Токен нового аккаунта должен иметь D1 Write; для `copy-r2` дополнительно R2 Read/Write; старому токену нужны D1 Read, R2 Read. Никогда не передавать токены в чат.
4. GitHub → Actions → `iumrah - Move old Cloudflare D1 (no hotel catalog)` → `dry-run`. Скачать артефакт `iumrah-cross-account-d1-counts`, сверить таблицы и строки.
5. При удовлетворительной проверке → `import`. Все целевые БД должны быть пустыми. Повторная запись поверх заполненной новой БД **запрещена**.
6. Затем → `copy-r2`. Целевой бакет `iumrah-operations-media` должен отсутствовать: скрипт создаст его и откажется перезаписывать существующие файлы. При ошибке проверьте R2-права, не переключая приложение.

## Критически важно до переключения

Этот workflow переносит **снимок данных**, не обеспечивает live replication. Пользователи могут продолжать писать в старые таблицы, пока идёт перенос. Непосредственно перед production cutover необходимо сделать финальную синхронизацию после остановки записи на старый Worker или настроить dual-write/replay, затем повторно сверить количества и ключевые значения. Нельзя считать один успешный `import` достаточным для cutover.

1. Перенести дополнительные KV namespaces/R2-объекты из других бакетов, если они используются, и проверить Durable Objects/Queues/cron/Workflows/AI bindings. D1 не содержит эти ресурсы.
2. Неизвлекаемые Worker secrets (JWT/HMAC, APNs, OAuth, сторонние API) повторно задать в **новом** Worker из защищённого источника. Иначе существующие сессии могут не пройти проверку, даже при наличии записей в D1.
3. Сохранить публичный домен `https://iumrah.app` и все прежние `/api/...` маршруты. В новой конфигурации Worker: `HOTELS_DB` → `iumrah-core`, `BOOKINGS_DB` → `iumrah-web-db`, `HOTELS_MEDIA` → `iumrah-operations-media`. Гостиничные endpoints переподключаются к новому внешнему API отелей, а не к удалённым таблицам.
4. Протестировать вход Apple/Google/телефон, создание и открытие брони, SMS/push, смену статуса, оплату, загрузку/чтение паспорта, билеты и тарифы, архив поездок и Business.
5. Держать старые D1, R2, Worker и маршруты **неизменёнными** до успешной финальной сверки и возможности rollback. Переход DNS/Workers routes должен идти только после тестового развёртывания нового сервера.

**Этот пакет не переключает клиентское приложение, Business или сайт и не отключает старые Worker.** Без повторного развёртывания серверных Worker и переноса авторизационных секретов нулевого перерыва гарантировать нельзя.
