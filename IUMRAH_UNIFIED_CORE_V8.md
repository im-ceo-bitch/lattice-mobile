# iumrah Unified Core V8 — порядок безопасного перехода

Единственный целевой Worker: https://iumrah-backend.helloiumrah.workers.dev. Внутри него пока три физические D1: iumrah-core (BOOKINGS_DB), iumrah-hotels (HOTELS_DB, включая аккаунты и операционные таблицы), iumrah-flights (FLIGHTS_DB). Новые маршруты Core, Package Engine, Hotels и Flight Hub обслуживаются одним Worker. Исходники перенесены; реальные записи из Cloudflare не скопированы и не проверены. Старые ресурсы сохранены для перехода и отката. Workflows не изменены.

## 1. Подготовка (до переключения клиентов)
- Применить Business ZIP. В Backend/IumrahBackend/core-bindings.json заменить `none` на точное имя существующего закрытого R2 bucket с паспортами (старый binding PASSPORTS); не делать его публичным. Если bucket в другом аккаунте, отдельно перенести объекты с исходными ключами и сверить количество и контрольные суммы. Сохранить также HOTELS_MEDIA и остальные существующие медиа.
- Запустить действующий Deploy iumrah backend. Сначала `IUMRAH_CORE_CUTOVER_READY` не включать. GET /__iumrah/health и /__iumrah/cutover — проверка наличия схем/привязок, НЕ подтверждение полноты данных.
- В Settings → Variables and Secrets единого Worker перенести существующие значения IUMRAH_SESSION_SECRET, IUMRAH_SUPERADMIN_PASSWORD, PACKAGE_QUOTE_SEAL_KEY (именно прежние значения), остальные ключи авторизации, SMS, Email, Telegram, Apple, APNS и поставщиков, если используются. AeroDataBox — AERODATABOX_RAPIDAPI_KEY и AERODATABOX_RAPIDAPI_KEY_BACKUP (с разрешёнными подписками). Не помещать ключи или дампы в Git, логи или чат.

## 2. Данные
- Определить фактические source/target D1 по привязкам старых Workers. Сделать резервные экспорты обеих сторон; выполнить финальную сверку при остановленных старых записях (включая фоновые задачи). Сырые брони/события/файлы метаданных — BOOKINGS_DB; аккаунты/сессии/паломники/поездки/операционные таблицы — HOTELS_DB; рейсы — FLIGHTS_DB. Не смешивать их вслепую.
- На защищённой локальной машине экспортировать SQL через Cloudflare D1 dashboard или `npx wrangler d1 export <точное-имя> --remote --output=<private.sql>` с проверкой аккаунта.
- Для каждой подтверждённой пары баз: `python Backend/CoreMigration/prepare_cutover.py old.sql target.sql --tables ALL --plan`. ALL только для действительно соответствующих целиком баз; иначе явно указать список таблиц. При конфликте остановиться, не перезаписывать реальные записи.
- После проверки плана: `python Backend/CoreMigration/prepare_cutover.py old.sql target.sql --tables ALL --output private-additions.sql`. Скрипт генерирует только проверенный добавочный SQL; исполнение отдельное, вручную через D1 после проверки целевой БД и резервной копии. Если схема отсутствует, сперва применить безопасные проверенные миграции/схему, не использовать старые reset-миграции. Не загружать private SQL в репозиторий.
- Снова экспортировать целевую D1: `python Backend/CoreMigration/prepare_cutover.py old.sql target-after.sql --tables ALL --verify`. Сверить реальные записи, ID, внешние ключи, историю, документы и доступ; не активировать Core при конфликте. Отдельно проверить R2.

## 3. Активация
- После сверки и остановки записей в старой системе установить секрет/переменную `IUMRAH_CORE_CUTOVER_READY=1` непосредственно в Worker. Перепроверить /__iumrah/cutover. Встроенный статус не подтверждает фактическую паритетность автоматически.
- Проверить вход клиента и сотрудника, существующую бронь и документ, создание тестовой брони и её видимость в Business, quote→commit, оплату/уведомления, чаты. Native Business может потребовать повторного входа из-за cookie прежнего хоста.
- Только после этого применить iOS ZIP и Web ZIP (Web workflow автоматически деплоит .uz). Запустить TestFlight для обеих iOS сборок. Текущая Web автоматизация обслуживает .uz; переключение .app/.us/.com и Android требуется подтвердить отдельно. Публичные ссылки на сайт остаются. Старые установленные версии приложений нужно обновить или перевести через совместимый proxy.
- Включить `IUMRAH_PACKAGE_CRON_ENABLED=1` только после остановки старого Package cron, чтобы не дублировать задачи/уведомления. Не удалять старый Worker, D1/R2, исходники или workflows до проверки и согласованного плана отката. Новый Worker использует один объединённый Cron.

Проверки: 37 unified + 39 Flight Hub + 86 Package runtime = 162; 7 тестов миграции; Swift smoke и Web edge/контрактные проверки. Не выполнены production deploy, проверка реальных секретов и данных, полноценные Xcode/Next.js сборки. Android не предоставлен. Не заявляется физическое объединение трёх D1.
