# iumrah — исправление существующего Deploy (Cloudflare D1 без R2)

Это **этап подготовки нового Cloudflare**. Старые данные и действующие API не изменяются.

## Причина предыдущего падения

Исходный `.github/workflows/deploy-hotels-cloud.yml` вызывает R2 API и получает ошибку 10042 (R2 не активирован). Даже если пропустить этот шаг, старый `render-config.mjs` пытается загрузить фотографии в R2 и привязать гостиничный R2 bucket. Продолжать старый гостиничный деплой в новый аккаунт небезопасно.

## Установка

1. Загрузите `iumrah-business-deploy-fix.zip` в **корень** репозитория iumrah Business. Текущий `apply-zip.yml` извлечёт только разрешённые файлы.
2. **Один раз** замените **существующий** файл `.github/workflows/deploy-hotels-cloud.yml` файлом `deploy-hotels-cloud.yml` из этого ответа. Не создавайте второй workflow. Причина отдельного шага: текущий распаковщик сознательно пропускает `.github/workflows/`.
3. Запустите в GitHub Actions существующий workflow (теперь называется `Deploy iumrah Cloud (D1 only)`). В Credentials используется `NEW_CLOUDFLARE_ACCOUNT_ID`/`NEW_CLOUDFLARE_API_TOKEN`, если они присутствуют, иначе текущие `CLOUDFLARE_ACCOUNT_ID`/`CLOUDFLARE_API_TOKEN`. Никаких новых Secrets не требуется.
4. Если `iumrah-flights` не найден, job остановится **до создания D1** — проверьте Account ID, не создавайте базы в старом аккаунте. Это защита от перепутанного Cloudflare.

## Что делает этот этап

- проверяет `iumrah-flights` в целевом Cloudflare;
- создаёт `iumrah-core`, если отсутствует, но **не перезаписывает** имеющуюся;
- применяет только `CREATE TABLE IF NOT EXISTS` для новой авиационной схемы;
- не использует R2, не запускает гостиничные SQL migrations и не развёртывает старый Worker;
- **не переключает** работающие `iumrah.app`, Business или iOS API.

## Что НЕ делает

**Этот этап ещё не копирует пользователей, бронирования, действующие авиабилеты и файлы из старого аккаунта.** Для этого потребуется защищённый экспорт исходных записей, проверка внешних ключей/документов и отдельная сверка перед cutover. Предыдущий артефакт аудита содержит только схему и счётчики, не саму базу.

Нельзя считать новую D1 продакшн-базой пользователей, пока не выполнена миграция реальных записей, авторизационных секретов и R2-документов.
