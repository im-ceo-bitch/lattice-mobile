# iumrah V21 — Backend Final Cutover / этап 1

**СТАТУС: код и локальные тесты готовы; production cutover НЕ выполнен.**

Основа: два полных ZIP от 13.11.2026, `lattice-mobile-main.zip` и `kepler-ios-main.zip`. Изменения только в Business; iOS исходники не менялись. Патч содержит только новые/изменённые файлы, без внешней папки; подходит к существующему `iumrah-business-*.zip` распаковщику. `.github/workflows` не затрагивается.

## Что исправлено

- Реальный deployment bootstrap теперь создаёт 16 недостающих таблиц и 17 индексов в `HOTELS_DB`: Apple/Google/Email и устройства, связи сессий, Gift Cards/Redemptions/Credit Ledger, Care, уведомления брони по Email. Использованы определения текущей миграции Package Engine и его действующих обработчиков; старые таблицы и строки не сбрасываются. Повторный запуск безопасен для проверенной схемы.
- Автоматическое обнаружение сохраняет существующие привязки `HOTELS_MEDIA` и `PASSPORTS` по настройкам уже опубликованного Worker. Не угадывает паспортный бакет, не переключает существующую привязку и не создаёт бакеты. При двух подходящих медиа-бакетах без явной привязки останавливается. Для явных имён используется `Backend/IumrahBackend/core-bindings.json`; пример прилагается, активный файл с выдуманным именем не добавлен.
- `Backend/CoreMigration/final_cutover.py`: сверка старых операций и бронирований с двумя текущими D1 по первичным ключам, всем исходным полям, дубликатам и FK; проверка ошибочно размещённых операционных таблиц из текущего `iumrah-core` и, симметрично, бронирований из `iumrah-hotels`. Конфликтующие строки, неизвестные таблицы и потеря существующей строки блокируют миграцию. Известные производные кэши и старый гостиничный каталог не импортируются; исходники не удаляются. Отчёт содержит названия таблиц и количества, не данные клиентов.
- Проверка R2 читает оба точных набора бакетов: `HOTELS_MEDIA` для операций, `PASSPORTS` для web booking documents. Проверяет SHA-256 содержимого всех старых объектов, читаемость всех целевых объектов из выбранных таблиц; ни один объект не перезаписывает. Бакеты проверяются даже при нуле объектов. Сама копия отсутствующих файлов не выполняется этой утилитой.
- `GET /__iumrah/cutover` отдельно показывает готовность схемы, наличие конфигурации провайдеров и факт операторской аттестации (не публикует значения ключей, количества или PII). Проверка деплоя перестаёт считать миграцию готовой по одному факту публикации Worker. Финальная проверка требует также наличия ключей SMS, Email, Apple/Google, Wallet, APNs, Telegram, eSIM; наличие конфигурации не означает успешность вызовов провайдера.
- Для доступа к private Core нужны прежний флаг `IUMRAH_CORE_CUTOVER_READY=1`, привязки D1/R2, существующие секреты и новая операторская аттестация `IUMRAH_CORE_PARITY_ATTESTATION=v21:<64 hex>`. Это намеренный дополнительный предохранитель. Аттестация — ID проверенных локальных снимков, а не криптографическое доказательство происхождения production-данных, поэтому оператор обязан проверять соответствие экспортов реальным ресурсам. Флаг и аттестация не включаются автоматически.

## 1. Подготовка и первый деплой

1. Убедиться, что сохранены backup старых и новых D1/R2 и определены точные UUID/имена по старым Workers. Не менять DNS/маршруты, не удалять старые Workers или базы. Если приложение уже использует старый Core в production, не включать режим остановки записи до согласованного окна и резервного плана.
2. Загрузить `iumrah-business-update-v21-backend-final-cutover.zip` в корень Business main. Дождаться Apply ZIP. Не добавлять новые workflows.
3. В существующем `iumrah-backend` убедиться, что `IUMRAH_CORE_CUTOVER_READY` отсутствует или равен `0`, а `IUMRAH_PACKAGE_CRON_ENABLED` не включён до завершения миграции. Сохранить старые секреты в Cloudflare, не менять их вслепую. Если существующая привязка PASSPORTS отсутствует, скопировать `core-bindings.example.json` в `core-bindings.json` и указать точные существующие имена (из Cloudflare, не из примера). Не указывать `iumrah-hotels-media` как паспортный бакет без проверки. Это имена ресурсов, не пароли.
4. Запустить существующий `Deploy iumrah backend`. Не менять его YAML. На данном этапе последний шаг Verify published backend **ожидаемо красный** с `CORE_CUTOVER_PENDING`, хотя Worker и additive schema могли успешно развернуться. Это сигнал незавершённой миграции, не ошибка сборки. При другом исключении (например, R2 lookup, schema incompatibility) остановиться, не обходить проверку.
5. Проверить `https://iumrah-backend.helloiumrah.workers.dev/__iumrah/cutover`. Сохранить лог Actions и JSON статуса (без приватных данных). Убедиться, что все группы schemaReady=true, исправить отсутствие binding/таблиц при необходимости. Не выставлять флаг `1`.

## 2. Какие D1 нужны для финальной сверки

Точные имена целевых D1 определены текущим workflow; исходные базы сверить по фактическим старым Worker bindings. Прежний cross-account workflow направлял операции из старой `iumrah-hotels` в новую `iumrah-core`, но V21 сервер продолжает использовать `HOTELS_DB` для операций. Не менять bindings вслепую: каталог в новой `iumrah-hotels`, raw booking store в новой `iumrah-core`.

| Приватный файл | Реальный источник | Назначение |
|---|---|---|
| `old-operations.sql` | старый D1 с аккаунтами, сессиями, Gift Cards, операциями | `HOTELS_DB` → текущая `iumrah-hotels` |
| `old-bookings.sql` | старый D1 web booking store (по прошлой схеме `iumrah-web-db`) | `BOOKINGS_DB` → текущая `iumrah-core` |
| `new-hotels.sql` | текущая `iumrah-hotels` | содержит существующие новые отели и операции |
| `new-core.sql` | текущая `iumrah-core` | текущие брони и, возможно, ранее ошибочно импортированные операции |

Экспортировать через D1 dashboard либо Wrangler от правильного Cloudflare account. Не передавать SQL с паспортами, хэшами токенов, аккаунтами, платежами в чат или GitHub. Хранить за пределами репозитория на защищённом диске. Не экспортировать пустую свежую базу вместо оригинала. Утилита проверяет обязательные старые таблицы; если они отсутствуют — это blocker, а не повод сгенерировать аттестацию на пустых таблицах. Если данные дополнительно существовали в третьей D1 (например, отдельный Telegram bot), её нужно отдельно проверить до релиза: V21 не переносит произвольные чужие DB.

В корне **Business** (после применения ZIP), с Python 3.11+:

```bash
# Подставить абсолютные пути к четырём приватным экспортам.
python3 Backend/CoreMigration/final_cutover.py \
  --legacy-operations /private/old-operations.sql \
  --legacy-bookings /private/old-bookings.sql \
  --target-hotels /private/new-hotels.sql \
  --target-bookings /private/new-core.sql \
  --mode plan
```

`plan` не пишет в Cloudflare. Сверить counts, `excluded`, `absent_optional_source_tables`, `misplaced_source_tables` и ошибки. Обязательно проверить известные старые таблицы, которые не попали в снимок. При одинаковом ключе и разных данных утилита останавливается: нельзя автоматически выбрать старую или новую строку. При исторической ссылке на отсутствующий hotel ID также остановиться и проверить, не подменять ID и не удалять документы. Скрипт не удаляет данные из неправильной базы — только планирует добавление в правильную.

## 3. Подготовка и импорт (только после сверки и остановки записи)

В согласованное окно остановить запись в старой системе (включая старые cron/ботов и другие writers), не допускать параллельных записей в целевые операционные таблицы. Повторно экспортировать все четыре D1. Повторить `plan` на свежих снимках. Затем запустить ту же команду, заменив последнюю строку на:

```bash
--mode prepare --old-writes-frozen --output-dir /private/v21-additions
```

Новый каталог должен отсутствовать; создаётся с правами 0700, SQL — с 0600. `HOTELS_DB.sql` предназначен исключительно для `iumrah-hotels`, `BOOKINGS_DB.sql` — для `iumrah-core`; файлы создаются только при наличии изменений. Скрипт не выполняет удалённый SQL. После ручной проверки backup, плана и целевой D1, применить только эти SQL к подтверждённой базе через Cloudflare D1 dashboard или `wrangler d1 execute <точная база> --remote --file=<private SQL>`. Не применять исходные дампы поверх заполненной D1. Не добавлять старые reset-миграции. После каждого импорта проверить результат, не продолжать при ошибке; новые снимки должны показать отсутствие pending statements.

После импорта снова экспортировать целевые D1. Повторить команду с `--mode verify-d1`. Это проверка совпадения сохранённых исходных строк, а не только количества строк; целевые новые строки сохраняются. Ноль pending statements ещё не означает проверку R2.

## 4. R2, секреты и активация

Сверить исходные и целевые точные имена обоих бакетов (операционные медиа и документы брони). Старые и новые аккаунты могут совпадать; исходный и целевой бакет должны соответствовать реальным Worker bindings. Если объекты отсутствуют, скопировать их с сохранением оригинального object key и Content-Type через утверждённую защищённую миграцию R2, не перезаписывая конфликтующие файлы. Для существующих бакетов не использовать старый скрипт, который создаёт новый бакет; для них требуется отдельно согласованное безопасное копирование. V21 проверяет байты, но не доказывает соответствие всех HTTP metadata и ACL: отдельно сверить приватность/метаданные. Документы должны быть недоступны без авторизации.

На доверенной машине, где `wrangler` доступен в PATH, установить переменные окружения с существующими Cloudflare credentials `OLD_CLOUDFLARE_ACCOUNT_ID`, `OLD_CLOUDFLARE_API_TOKEN`, `NEW_CLOUDFLARE_ACCOUNT_ID`, `NEW_CLOUDFLARE_API_TOKEN` (только из защищённого источника, без вывода в консоль или чат). Для `verify` достаточно R2 read и возможности читать metadata бакета. Выполнить ту же команду с последними аргументами:

```bash
--mode verify --old-writes-frozen \
  --old-media-bucket EXACT_OLD_MEDIA \
  --new-media-bucket EXACT_NEW_MEDIA \
  --old-passports-bucket EXACT_OLD_PASSPORTS \
  --new-passports-bucket EXACT_NEW_PASSPORTS
```

Только после нулевых pending statements, проверки байтов, ручной сверки источников/исключений и подтверждения остановки старых writers результат содержит `operator_attestation`. Не генерировать строку вручную. Убедиться, что актуальные bindings у deployed Worker соответствуют этим экспортам. Утилита не активирует Worker и не выполняет live login/booking.

В Cloudflare → Workers & Pages → `iumrah-backend` → Settings → Variables and Secrets, не в Git:
- сохранить прежние значения `IUMRAH_SESSION_SECRET`, `IUMRAH_SUPERADMIN_PASSWORD`, `PACKAGE_QUOTE_SEAL_KEY`; проверить все существующие ключи провайдеров (SMS/Email/Wallet/APNs/Telegram/eSIM); ключи не пересоздавать вслепую;
- после выполнения всех проверок установить `IUMRAH_CORE_PARITY_ATTESTATION` равным строке из отчёта;
- **только после этого** установить `IUMRAH_CORE_CUTOVER_READY=1`.

Повторно проверить `__iumrah/cutover` и запустить тот же Deploy workflow. Если последний шаг сообщает `CORE_PROVIDER_CONFIGURATION_PENDING`, это недостающая конфигурация, а не повод отключать проверку. Если миграция неудачна или тесты авторизации/доступа к документам выявили проблему, снять флаг готовности (0), использовать утверждённый rollback старого клиента/маршрутов, не удалять старые данные. При уже начавшихся записях в новую базу rollback требует отдельной сверки обратного потока; не включать старые writes вслепую.

## 5. Что остаётся перед App Store

- Реальные существующие аккаунты, Apple/Google/SMS/Email/password, восстановление и сеансы, Wallet pass.
- Реальные существующие брони, sealed quote→commit→Business, тестовые данные/чеки/документы с проверкой ACL, Gift Cards и кредит, Care, чаты, APNs/Telegram/email, eSIM. Проверка на выделенных тестовых аккаунтах и бронях; не создавать дубли реальных платежей.
- Umrah Advisor, молитвы, погода, валюты пока ещё имеют прямые обращения в iOS. Не переносились в V21 этап 1. Android/Web не предоставлены в этих ZIP. Старый Package Engine не удалён до подтверждения cutover.
- Xcode/TestFlight, реальный Cloudflare deploy и внешние provider calls не запускались в локальной среде. Зелёный результат проверок в CI подтверждает только проверенные условия; полноценный release — после authenticated production smoke tests и TestFlight.
